# GPC — Gravity Connect Five 9×7

**المهمة:** تحديد القيمة النظرية للوحة فارغة 9×7، Connect‑5، بالجاذبية، وإخراج شهادة استراتيجية قابلة للتحقق مستقلًا.

هذه الحزمة تنقل المشروع من Phase 1 وPhase 2 إلى بنية Phase 3 الموزعة. لا تعلن أن اللعبة حُلّت: الحالة الابتدائية تظل **UNRESOLVED** إلى أن ينتج البحث شهادة جذر كاملة ويقبلها المدقّق المستقل.

## ما يتضمنه المستودع

- `phase1/`: نموذج 9×7، هندسة خطوط الفوز، انعكاس اليسار/اليمين، وGravity‑Tempo Reachability.
- `phase2/`: محرك AND/OR، القواعد التكتيكية المثبتة، مولّد الشهادات، المدقّق المستقل، وشهادات 9×7 للحالات الوسطية.
- `src/gravity_watcher_native.cpp`: محرك C++17 للبحث الإثباتي Gravity‑DFPN مع ذاكرة قابلة للحفظ والاستعادة.
- `scripts/run_worker.py`: عامل مستقل يستأنف التزام إثبات واحدًا ويحفظه في GitHub Release.
- `scripts/worker_batch.py`: يوزع أربعة التزامات على كل آلة قياسية ذات أربعة أنوية.
- `scripts/make_certificate_from_dfpn.py`: يحول جدول الحالات المحسومة إلى شهادة AND/OR مستقلة.
- `scripts/aggregate_root.py`: يعكس الفروع المتناظرة، ثم يجمع 162 فرعًا منطقيًا ويبني شهادات الجذر.
- `.github/workflows/gpc-phase3.yml`: تشغيل 21 مجموعة، مع حد أقصى 20 آلة متزامنة.

## النتيجة الرياضية المطلوبة

نبحث قضيتين مستقلتين لكل لاعب مستهدف:

- `target_win`: اللاعب المستهدف يستطيع فرض الفوز.
- `target_not_win`: اللاعب المستهدف لا يستطيع فرض الفوز.

لا يُحوّل انتهاء الوقت أو بلوغ سقف الذاكرة إلى نتيجة. يبقى الفرع غير المكتمل `unresolved`.

النتيجة النهائية تُعلن فقط بهذه الشروط:

- فوز اللاعب الأول: شهادة جذر `target_win` للاعب 0.
- فوز اللاعب الثاني: شهادة جذر `target_win` للاعب 1.
- تعادل: شهادتا جذر `target_not_win` لكل من اللاعبين.
- غير ذلك: `UNRESOLVED`.

كل شهادة جذر تمر عبر `verify_certificate` في `phase2/gpc_phase2.py`، وهو لا يستدعي محرك DFPN الذي أنشأ بيانات البحث.

## تشغيل البحث الموزع

بعد نشر الملفات إلى `main` يبدأ الـworkflow تلقائيًا بسبب `push`، ويمكن تشغيله يدويًا من تبويب Actions عبر `workflow_dispatch`.

كل مجموعة تشغّل حتى أربعة عمليات بحث مستقلة على آلة واحدة. تُستخدم حتى 20 آلة بالتوازي؛ أي حتى 80 عملية بحث مستقلة موزعة على 20 آلة، مع استهلاك لا يتجاوز عدد أنوية الآلة الواحدة. كل التزام إثبات له ملف checkpoint خاص به.

### اختزال التناظر

الانعكاس الأفقي اختزال دقيق للعبة. لذلك لا نبحث كل الافتتاحات التسعة منفصلة:

- الافتتاحات الأولى الممثلة: الأعمدة 0 إلى 4.
- عند الافتتاح في العمود 0 إلى 3، نبحث ردود الخصم التسعة.
- عند الافتتاح في العمود الأوسط 4، نبحث الردود 0 إلى 4 فقط؛ البقية انعكاس لها.
- نبحث الهدفين 0 و1.

إجمالي التزامات البحث الفعلية: `2 × (4 × 9 + 5) = 82`، وتغطي بالانعكاس كل `2 × 9 × 9 = 162` فرعًا منطقيًا بعد نقلتين.

## الحفظ والاستئناف

تُحفظ ذاكرة DFPN في ملف ثنائي يتضمن هوية الجذر، واللاعب المستهدف، والسعة، ومفاتيح الحالة الكاملة 128‑bit، وأرقام الإثبات والنفي، ومعلومات حدود الأفق. لكل عامل فتحتان A/B؛ تُرفع النسخة الجديدة أولًا ثم يُحدّث manifest للإشارة إليها. عند فشل الرفع تبقى النسخة السابقة صالحة.

تُحفظ نقاط التوقف في GitHub Release ثابت باسم `gpc-phase3-checkpoints`، لا في مجلد مؤقت ولا في Actions Cache. ملفات نتائج التشغيل وملفات الشهادات تُرفق أيضًا كـArtifacts لتسهيل قراءة الجولة.

## حدود مهمة

- كل فرع مدته القصوى التشغيلية 18,400 ثانية (نحو 5 ساعات و6 دقائق) في الجولة الواحدة. يمكن إعادة تشغيل الـworkflow؛ يستأنف العامل من آخر checkpoint منشور.
- أربع عمليات على آلة 4‑vCPU لا تعني أربع آلات؛ كل عملية تشغل نواة واحدة تقريبًا.
- لا يُضمن أن تنتهي لعبة 9×7 في جولة واحدة. القيمة الوحيدة المقبولة هي شهادة الجذر المتحققة، لا أرقام PN/DN أو عدد العقد.
- يطبّق DFPN اختزالات تكتيكية مبررة رياضيًا، بينما تبقى درجات Gravity‑Lambda لترتيب النقلات فقط ولا تُستخدم لحذف فروع قانونية.
- يجب مقارنة قواعد النموذج بلوحة قواعد اللعبة الأصلية قبل اعتماد أي نتيجة نهائية.
